## 三、P0 致命问题修复详情

### 3.1 engine.c: free() 与 lv00_free() 混用 → 已修复

**文件**：`src/core/engine.c`
**问题**：`engine_handle_circuit_trip_with_action()` 中 DOWNGRADE 分支使用标准 `free()` 释放通过 `symbolic_coord_create_rational()` 分配的内存，而该函数内部使用 `lv00_malloc`。如果 `lv00_malloc` 添加了 `AllocHeader`，使用标准 `free()` 会导致未定义行为。
**修复**：将 `free(new_coord)` 替换为 `lv00_free((void **)&new_coord)`。

### 3.2 memory_pool.c / thread_pool.c: malloc/free 使用 → 设计确认

**文件**：`src/core/memory_pool.c`, `src/core/thread_pool.c`
**问题**：两个底层基础设施模块大量使用标准 `malloc`/`free` 而非 `lv00_malloc`/`lv00_free`。
**评估**：这是**有意为之的设计决策**——底层模块不能依赖可能使用这些模块的上层分配器，否则会形成循环依赖。
**修复**：在两个文件头部添加了详细的设计说明注释，明确使用约定（pool 分配的对象必须通过 pool_free 释放）。

### 3.3 solver_core.c: CDCL 空桩返回 SATISFIED → 已修复

**文件**：`src/core/solver_core.c`
**问题**：CDCL 求解器核心所有步骤（传播、冲突检测、冲突分析、回跳、学习、决策）均为空桩，但步数耗尽和决策资源耗尽时返回 `CDCL_SATISFIED`（即 SAT）。调用者会认为约束系统已被满足，但实际上求解器什么都没做——这是**静默正确性错误**。
**修复**：
- `cdcl_run()` 末尾：`CDCL_SATISFIED` → `CDCL_IDLE`（返回 UNKNOWN）
- `cdcl_step_decide()` 资源耗尽：`CDCL_SATISFIED` → `CDCL_IDLE`

### 3.4 solver_core.c: remove_constraint 不真正移除 → 已修复

**文件**：`src/core/solver_core.c`
**问题**：`lv00_solver_remove_constraint()` 仅标记 `constraint_failed[constraint_id] = true`，但不更新 CDCL 子句计数，导致后续求解逻辑不一致。
**修复**：添加 `orig_clause_count--` 逻辑（带防下溢保护），并完善注释说明桩实现的局限性。

### 3.5 proof.c: strcpy 缓冲区溢出风险 → 确认安全

**文件**：`src/core/proof.c`
**问题**：审查报告指出多处 `strcpy` 可能导致缓冲区溢出。
**验证结果**：经逐行检查，所有字符串复制操作已使用安全的 `snprintf`，并带有明确的安全注释。**无需修复**。

## 四、P1 严重问题修复详情

### 4.1 engine.c: new_func_block_id 推断假设 → 已修复

**文件**：`src/core/engine.c`
**问题**：`new_func_block_id = engine->main_graph->next_node_id - 1` 假设 `graph_add_function_block()` 只添加一个节点，但该函数可能添加多个内部节点。
**修复**：添加安全范围检查，ID 无效时返回 `ENGINE_ERROR_INTERNAL`。

### 4.2 proof_trace.c: 递归销毁无深度保护 → 已修复

**文件**：`src/core/proof_trace.c`
**问题**：`proof_tree_node_destroy_recursive()` 是纯递归实现，无深度限制。恶意或异常输入可能导致栈溢出。
**修复**：添加 `PROOF_TREE_DESTROY_MAX_DEPTH = 10000` 深度限制，超限时输出警告并释放当前节点（不递归子节点）。

### 4.3 Python 异常体系不统一 → 已修复

**文件**：`python/lv00/engine.py`, `python/lv00/func_block.py`
**问题**：`EngineError` 和 `FuncBlockError` 独立继承 `Exception`，而非 `Lv00BaseError`，导致无法统一捕获。
**修复**：
- `EngineError(Exception)` → `EngineError(Lv00BaseError)`
- `FuncBlockError(Exception)` → `FuncBlockError(Lv00BaseError)`
- 删除重复的 `__init__`/`__str__` 方法

### 4.4 版本号不一致 → 已修复

| 文件 | 修复前 | 修复后 |
|------|--------|--------|
| `python/lv00/__init__.py` | 3.2.0 | 3.3.0 |
| `package.json` | 3.2.0 | 3.3.0 |
| `concurrent_monitor/__init__.py` | 3.2.0 | 3.3.0 |

### 4.5 api_server.py 硬编码默认密码 → 已修复

**文件**：`llm_coding_assistant/api_server.py`
**问题**：默认管理员密码为 `"admin123"`，存在安全风险。
**修复**：改为从环境变量 `LV00_ADMIN_PASSWORD` 读取，未设置时自动生成随机临时密码并打印警告。

### 4.6 constraint_graph.c 双轨错误系统 → 确认已统一

**验证结果**：该文件已完全使用 `lv00_set_error()`/`lv00_clear_error()`，不存在双轨问题。
