## 二、详细分析

### 2.1 多线程安全性验证

#### 问题描述
`func_block_instantiate.c` 第116行原使用 `graph->next_node_id++` 进行节点ID分配，在多线程环境下可能导致数据竞争。

#### 解决方案
**constraint_graph.h** 中已实现：
```c
/* v3.4.1: 多线程安全原子操作宏 */
#define GRAPH_ATOMIC_NODE_ID_INCREMENT(graph) \
    atomic_fetch_add_explicit(&((graph)->next_node_id), 1, memory_order_relaxed)

/* ConstraintGraph 结构体中 */
_Atomic int next_node_id;       /* 下一个可分配的节点 ID（原子操作，线程安全） */
_Atomic int next_constraint_id;  /* 下一个可分配的约束 ID（原子操作，线程安全） */
```

**func_block_instantiate.c** 中的使用：
```c
/* 分配新ID（v3.4.1: 多线程安全实现完成） */
copy->id = atomic_fetch_add_explicit(&graph->next_node_id, 1, memory_order_relaxed);
```

#### 优化效果
- ✅ 节点ID分配线程安全
- ✅ 无锁算法实现高性能
- ✅ 使用 memory_order_relaxed 优化并发性能

### 2.2 引用计数安全机制验证

#### 问题描述
`func_block_registry.c` 的 `cleanup` 函数需要确保在外部仍有引用时不会产生悬空指针。

#### 解决方案
**PresetEntry 结构体**（func_block_registry.h）已包含引用计数字段：
```c
typedef struct {
    char *name;
    char *description;
    PresetCategory category;
    FuncBlock *template_fb;
    int ref_count;  /* 引用计数 (v3.4.1)：模板函数块的引用数量 */
} PresetEntry;
```

**free_preset_entry 函数**（func_block_registry.c）实现引用计数安全释放：
```c
/* 引用计数安全释放：仅当无外部引用时才释放模板函数块 */
if (entry->template_fb) {
    if (entry->ref_count <= 1) {
        /* ref_count == 1 或 == 0（理论上不应该），安全释放 */
        func_block_destroy(entry->template_fb);
    }
    /* ref_count > 1：保留 template_fb，避免悬空指针 */
}
```

#### 优化效果
- ✅ 注册表清理不会产生悬空指针
- ✅ 外部代码可安全使用 lookup 返回的深拷贝
- ✅ 注册表可安全重新初始化

### 2.3 统一错误系统实现

#### 问题描述
需要将每图级错误缓冲区迁移到 Lv00Context 统一错误系统。

#### 解决方案
**graph_set_error / graph_get_error 函数**实现优先使用 context 存储：
```c
/* 优先使用 context 错误存储 */
if (graph->context) {
    vsnprintf(graph->context->error_message, 
               sizeof(graph->context->error_message), fmt, args);
} else if (graph->error_buffer) {
    /* Fallback 到 error_buffer */
    vsnprintf(graph->error_buffer, 256, fmt, args);
}
```

#### 遗留缓冲区说明
- `error_buffer` 和 `serialize_buffer` 作为 fallback 保留
- 向后兼容，避免破坏已有调用代码
- v3.4.0 计划中：待 Lv00Context 完全就绪后完全迁移

### 2.4 内部公共API依赖说明

#### 问题描述
`preset_common.h` 引用了 `lv00_internal.h`，可能被认为破坏了公共API封装。

#### 解决方案
更新文件头注释，明确内部公共API定位：
```c
/**
 * 【内部公共API说明】
 * 此头文件位于 include/lv00/ 目录，虽然是"公共"头文件，
 * 但实际上是供 src/ 目录下的内部模块使用的内部公共API，
 * 不是供外部库用户直接使用的外部公共API。
 *
 * 此头文件依赖 lv00_internal.h 和 lv00_utils.h，因为：
 *   - LV00_ERROR_SET 等错误处理宏
 *   - lv00_malloc 等内存管理函数
 *   - lv00_safe_* 等安全字符串函数
 *   - lv00_log_* 等日志函数
 */
```

#### 提升为真正外部公共API的路径
如需将此头文件提升为真正的外部公共API，应：
1. 将必要的错误码定义提取到 error_codes.h
2. 将内存管理函数声明提取到独立的公共头文件
3. 将安全字符串函数声明提取到公共头文件
