# Lv-00 双模式执行模型设计（解释 + 可选编译为机器码）

> 状态：设计草案 v0.1（2026-08-27）
> 动机：用户「弄成两种模式——也可以可选编译成机器码；CPython 和 Python 的比喻」
> 类比：CPython 的**解释器**（默认）与 **Cython/C 扩展**（编译加速）双路径；
>       Java 的**解释器 + JIT**；LuaJIT 的 trace 编译
> 决策原则：**默认解释（交互/调试/正确性优先），可选编译（性能/部署优先）**

---

## 0. 现状执行模型（已核实）

```
DSL 源码 → Tokenizer → AST → [dsl_compile: AST→IR] → [dsl_ir_to_constraint_graph: IR→图]
                                     ↑ 真正的编译        ↑ 解释执行（VTable 分发 30 操作码）
→ 约束求解 → 证明 → [interop_export_lean/coq: 证明→源码]
                    ↑ 源码级编译（到外部证明助手的源语言）
```

- **现状主体是解释型**：IR 存在，但逐条 VTable 分发执行（无字节码/机器码）。
- **已具备的编译相关设施**（全部可复用）：
  - `ga_codegen`：C/C++/CUDA/Python/LaTeX/DOT **六目标代码生成**（先例）
  - `lv_dlopen/lv_dlsym/lv_dlclose`：动态加载（plugin_system_load.c）
  - `lv_external_process_run`：子进程执行外部编译器
  - `interop_export_lean/coq`：证明源码级编译后端

## 1. 双模式设计（核心）

```
                    ┌────────────────────────────────────┐
                    │          DSL 编译管线（共用）        │
                    │  tokenize → parse → compile(AST→IR) │
                    └──────────────┬─────────────────────┘
                                   │ IR
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
          ┌─────────────────┐           ┌───────────────────┐
          │  模式 A：解释执行  │           │  模式 B：编译执行    │
          │  (默认)          │           │  (可选)            │
          │  IR→图 VTable    │           │  IR→C 代码生成      │
          │  逐条分发         │           │  → 编译 .so/.dll   │
          │  交互/调试/小规模  │           │  → lv_dlopen 加载   │
          └─────────────────┘           └───────────────────┘
```

### 模式 A：解释执行（现状，默认）

- `dsl_ir_to_constraint_graph` 现有 VTable 分发，**不改**。
- 适用：交互式 REPL、调试（可插桩/断点）、小规模、正确性优先。

### 模式 B：编译执行（可选，新增）

- `dsl_ir_to_constraint_graph_compiled(ir, graph)`：
  1. **IR → C 代码生成**（复用 ga_codegen 的 emit 模式，新写 `ir_codegen_c.c`）；
  2. 生成的 C = 与解释路径**语义等价**的图构造函数
     （`static void build_graph(ConstraintGraph *g) { ... }`）；
  3. 编译为共享库（调 `lv_external_process_run(cc, ...)` 或本地 cmake）；
  4. `lv_dlopen` + `lv_dlsym("build_graph")` 加载执行。
- 适用：大规模批量、L9 分片 worker（编译一次，多分片复用）、部署。

## 2. 类比语言对照

| 类比 | 解释路径 | 编译路径 | Lv-00 对应 |
|---|---|---|---|
| CPython | py 解释器 | Cython/C 扩展 | 模式 A / 模式 B |
| Java | 解释器 + JIT | JVM 字节码 | 模式 A / （未来 JIT） |
| LuaJIT | 解释器 | trace JIT 编译 | 模式 A / 模式 B（AOT） |
| Cython | — | Python→C→机器码 | 模式 B（IR→C） |

**Lv-00 与这些的差异**：DSL 输出是**约束图 + 证明**（数据结构），非通用程序。
所以"编译成机器码"的收益点不在通用计算，而在：
1. **消除 IR 解释分发开销**（VTable 查表 → 直接 C 调用序列）；
2. **消除重复解析编译**（一次编译 → 多次加载，对照 .class 缓存）；
3. **分片 worker 部署**（预编译 worker 二进制，免运行时解析）。

## 3. 编译生成的 C 代码形态（示例）

DSL 输入：
```
point A 10 20;
point B 30 40;
line a A B;
```

生成的 C（模式 B 产物）：
```c
/* Auto-generated by lv_dsl_codegen (C target) */
#include "lv/constraint_graph.h"
#include "lv/symbolic_coord.h"

void lv_dsl_build_graph(ConstraintGraph *g) {
    SymbolicCoord *ax = symbolic_coord_create_rational(10, 1);
    SymbolicCoord *ay = symbolic_coord_create_rational(20, 1);
    SymbolicCoord *ac[2] = {ax, ay};
    int A = graph_add_point(g, ac, 2);
    symbolic_coord_destroy(ax); symbolic_coord_destroy(ay);
    /* ... B, line a A B ... */
}
```

- **语义等价保证**：生成代码与解释路径调用同一组图 API；
  测试对比两条路径产出的图（`meta_repr_graph_equivalent`）应等价。
- **符号表**：IR 符号 → C 变量名映射（`A` → `int A`），
  避免名称冲突用 `_v{n}` 前缀。

## 4. IR 代码生成模块划分

```
core/src/layer4_reasoning/dsl/
├── ir_codegen_c.c      # IR → C 源码生成（~600-900 行）
├── ir_codegen_compile.c # 调外部编译器生成 .so/.dll（~200-300 行）
├── ir_codegen_load.c    # lv_dlopen 加载 + 调用（~150-250 行）
├── ir_codegen_cache.c   # 编译产物缓存（源码 hash → .so 复用，~200-300 行）
└── ir_codegen.h         # 公共 API：lv_ir_compile_to_native / lv_ir_load_native
```

### 4.1 缓存设计（对照 .class / .pyc）

- 缓存键 = DSL 源码 SHA-256 + Lv-00 版本。
- 缓存位置：`<cache_dir>/lv_ir_<hash>.so`。
- 命中 → 直接 dlopen；未命中 → 生成+编译+写缓存。
- 与 L9 证书的 content-hash 哲学一致（能落盘的绝不重算）。

### 4.2 编译器选择

- 开发环境：本地 cc/gcc（复用 lv_external_process_run）。
- 生产/部署：预编译 worker 镜像（L9 分片），无运行时编译器依赖。
- 失败降级：编译失败 → 回退模式 A 解释执行（双模式的安全网）。

## 5. 双模式的切换 API

```c
/* 编译并加载 DSL 为原生构造函数（模式 B） */
typedef void (*lvDslBuildGraphFn)(ConstraintGraph *graph);

lvDslBuildGraphFn lv_ir_compile_to_native(const char *dsl_source,
                                          const DslCompileConfig *cfg,
                                          char **out_error);

/* 一键执行：自动选择模式（可配置） */
bool lv_dsl_execute(const char *source, const DslCompileConfig *cfg,
                    ConstraintGraph *graph, lvDslExecMode mode);
```

```c
typedef enum {
    LV_DSL_EXEC_INTERPRET = 0,  /* 模式 A（默认） */
    LV_DSL_EXEC_COMPILE,        /* 模式 B（强制编译） */
    LV_DSL_EXEC_AUTO            /* 自动：编译缓存命中则编译，否则解释 */
} lvDslExecMode;
```

- `LV_DSL_EXEC_AUTO`：**默认建议**——小输入/首次走解释，重复/大规模走编译缓存。
  类比 Java 的解释器预热 + JIT 提升。

## 6. 收益量化（预估）

| 场景 | 解释模式开销 | 编译模式收益 |
|---|---|---|
| 图构造（IR 分发） | VTable 查表/条 | 直接 C 调用序列（省查表） |
| 重复加载同一 DSL | 每次重新 parse+compile | 缓存命中，零解析 |
| L9 分片 worker | 每 worker 运行时解析 | 预编译 worker，零解析 |
| 大规模批量（10k 点） | 解释分发累积 | 编译后线性速度 |

- **注意**：几何求解（Groebner/数值）是主要耗时，图构造解释开销占比小。
  双模式的主要收益在**部署/复用**（消除重复解析、worker 预编译），
  而非图构造本身的微秒级分发。文档明确此边界，避免过度承诺。

---

## 7. 与 L9 调度层的关系

- **分片 worker 用模式 B**：DSL 分片输入 → 预编译 worker → 多分片复用。
- **证书验证用模式 B 的编译能力**：L9 证书正文（Lean/Coq）已是编译验证；
  本设计的 IR→C 是**另一条编译路径**（图构造），两者互补：
  - IR→C：把"怎么构造图"编译成机器码（性能/部署）；
  - Lean/Coq：把"证明为什么正确"编译成可验证源码（可信）。
- 可统一为 L7 编排的阶段产物：`[编译产物: .so 或证书]`。

## 8. 与已有代码生成的关系

- `ga_codegen`：多维向量 → C/C++/CUDA（数学内核）。
- 本设计：DSL IR → C（图构造内核）。
- **统一模式**：两者都是"内部表示 → 目标语言源码 → 编译/加载"。
  未来可共享 codegen 基础设施（emit 工具、编译调用、缓存）。

## 9. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 生成 C 与解释语义不一致 | 双路径等价测试（meta_repr_graph_equivalent） |
| 编译依赖（cc 不存在） | 失败降级模式 A；生产用预编译 |
| 缓存失效（版本升级） | 缓存键含 Lv-00 版本 |
| 动态加载安全（dlopen 恶意 .so） | 只加载缓存目录内、由本系统生成的产物 |
| 过度承诺性能 | 文档明确收益在部署/复用，非图构造微秒级 |

## 11. 实施顺序建议

1. `ir_codegen_c.c`：IR→C 生成（先覆盖高频操作码：点/线/圆/约束）。
2. 等价性测试：解释 vs 编译产出的图必须等价。
3. `ir_codegen_compile.c` + `load.c`：编译 + dlopen 加载。
4. `ir_codegen_cache.c`：产物缓存（对照 .class）。
5. `lv_dsl_execute` 双模式 API + AUTO 模式。
6. 接入 L9 分片 worker（模式 B 预编译）。
